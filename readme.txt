KiroCrew 内置 Agent 分叉改造

目标
- 彻底移除 ACP 和外部 Agent CLI 的运行依赖.
- 保留现有 Web、会话、记忆、技能、MCP、定时任务和任务编排功能.
- 支持在界面设置模型 URL、API key 和模型, 自行运行模型与工具调用循环.
- 单用户内网部署, 去掉 Gateway token 登录要求.
- 保留实现与测试代码, 不把未验证的功能标记为完成.

超时约束
- 所有终端命令都使用 timeout -k, 不运行无限等待的测试或安装.
- 模型设置 HTTP: 15 秒; 浏览器操作: 15 秒, 导航: 20 秒.
- 内置 Agent 初始化: 总计 90 秒; MCP 初始化: 每服务 60 秒.
- MCP 实际工具请求与调用方等待: 180 秒; 关闭: 10 秒.
- 模型流连接: 30 秒, 无数据读取: 180 秒; 单轮默认总预算 1800 秒, 覆盖排队、初始化、压缩和工具循环.
- 停止生成: 默认最多等待 10 秒确认清理, 支持调用方更短预算; 初始化阶段也可取消.
- MCP 调用方取消会传递到实际请求, 超时或取消后连接可继续处理下一项请求.
- 配置写锁: 非阻塞, 占用时立即返回 HTTP 409, 不留下无限排队的迟到写入.
- 后台 prompt 的预算覆盖会话锁等待与执行, 未传预算默认 1800 秒.
- direct 工具等待消费方审批的执行侧预算为 180 秒, 取消时清理待决请求.
- 命令工具: 默认 120 秒, 最大 1800 秒, 超时清理进程组.

决策与经过记录 (2026-10-24)

1. 为什么改为内置 Agent
- 原项目由外部 Agent CLI 通过 ACP 承担模型连接、工具循环和原生会话.
- 用户希望保留 KiroCrew 的界面、记忆、技能、MCP 和任务编排, 由自己配置模型地址与 key, 不依赖外部 Agent CLI 或网页登录.
- 因此最终设计是 DirectProvider 自己请求 Chat Completions 并执行工具循环, 复用已有业务层, 而不是给旧 CLI 增加一个模型代理.

2. 为什么前面工作时间过长, 后来调整交付标准
- 实施过程中逐步发现会话恢复、取消、工具身份、审批与模型选择仍耦合旧运行时, 修复范围不断扩展.
- 助手先采用保留旧接口、逐步替换的方式, 让主流程较早可运行, 但也留下兼容别名与新旧结构并存的包袱. 这不是用户要求的最终简洁设计, 不能把阶段性可用表述为彻底改造完成.
- 用户明确这是个人使用项目, 要按触发概率、影响、复现难度与修复成本取舍, 不追求消灭所有 bug, 不为低概率场景持续追加适配代码.
- 据此停止扩展边界修复, 以模型设置、聊天、工具执行与审批、会话恢复和页面启动为主要验收项. 有明确实际故障时修复根因, 不为了假想风险继续铺框架.
- 用户随后明确授权开发阶段清理重建: 以最终设计为准删除旧实现、无用转发与失效测试, 不要求兼容探索中间状态, 不要求清空 Git 历史或工作区改动.

3. 本轮清理的具体经过
- 审阅 Git diff 后删除约千行不可达网页认证流程与 47 个无用导入, 删除前端 ACP adapter 转发与注册别名.
- 继续删除外部 CLI 安装登录门禁、空 DashboardBootstrap 包装、对应状态/修复/升级路由与处理器, 同步移除专属失效测试. 页面直接挂载 App.
- 新数据目录启动发现旧状态处理器引用已删除的门禁 owner 判断, 改为直接引用现有共享 owner 判断函数, 没有恢复旧文件或添加兼容模块.
- 新数据目录未配置模型时仍尝试创建后台会话, 已改为配置模型后再创建; direct 启动地址不再生成 token 链接.
- 配置保存后实际出现每两秒重试外部 Agent spec 重建的错误. 原因是旧配置监听器仍假定默认模型必须写进共享 ~/.kiro/agents spec, 而临时实例没有该目录的重写权.
- direct 的默认模型由配置与内置工厂决定, 不需要这次外部 spec 重建. 已让 direct 模型回调直接刷新界面, 不调用旧重建; 内存回调验证确认重建调用次数为零.
- 独立临时数据目录完成初始化、空配置表单、正式 API 保存模型、真实工具审批、cron_list 和模型续答. 没有复制旧数据库, 但仍使用当前用户已有 Agent spec, 因而不是完全隔离的全新系统安装证明.
- 临时实例与临时数据已清理, 正常使用实例重启加载最新代码. 本轮 43 项 direct 回归、前端类型检查、生产构建及最终设置页面验证通过. 此处不表示每次清理后都重新执行了之前全部 578 项相关测试.

4. 为什么不能称为源码级彻底移除 ACP
- 当前模型工厂只创建 DirectProvider, 日常模型与工具循环已由内置运行时执行. 这证明默认执行路径已替换, 不证明整个源码树不再依赖 ACP.
- 2026-10-24 只读核查确认, src/kiro_crew/acp/client.py、acp/runtime.py、providers/acp.py 仍存在.
- session.py 仍保留旧 provider 类型判断、加载入口、ACP runtime 与进程辅助函数引用; config/sections_agent.py 仍有 acp_backend、member_acp_backend 字段.
- agent_sdk/drivers/acp_turn_vocab.py 仍从 acp.transport_errors 读取异常类型, 其他共享定义也有旧路径兼容引用.
- 因此现在直接删除整个 acp 目录仍可能导致导入或调用失败. 尚未完成删除是实现范围未完成, 并非技术上不能删除, 也不是为了方便上游同步而必须保留.
- 真正完成标准: 把仍有效的共享定义放入协议中立模块, 更新有效调用点, 删除旧执行器、废弃配置与专属测试, 不添加新的旧接口包装, 再验证启动及个人使用主流程.

5. 未来如何吸收主仓库更新
- 2026-10-24 核查: 当前分支 main; 只有 origin, 指向经 gh-proxy.org 访问的 yanguangshaonian/KiroCrew fork; 尚未配置 upstream.
- 当时改造仍包含大量未提交修改. 同步上游前先提交并保存已验收版本, 可以打稳定标签作为恢复点. 本次仅说明流程, 没有执行提交、打标签、配置 upstream、fetch 或 merge.
- 确认官方主仓库地址后添加 upstream. 先 fetch 查看变化, 在独立集成分支或 worktree 中处理更新, 正常实例继续运行稳定版本, 不在运行实例的工作树中直接合并或切换源码.
- 小而独立的修复适合挑选提交; 大批仍适用的功能可合并后解决冲突; ACP 或外部 CLI 改动通常只提取需要的业务逻辑, 不直接恢复已删除的运行流程.
- 独立 UI、文档和工具修复通常较易吸收; 记忆、任务和子任务编排需核对接口; 会话生命周期、上下文与审批较容易冲突; ACP、安装登录和后端选择通常与本分叉目标不同.
- 建议长期分叉采用合并或挑选提交, 不反复把整条改造分支 rebase 到上游最新版本, 避免反复解决相同冲突. 这是维护建议, 不是已经执行的 Git 操作.
- 个人使用无需追每个上游提交, 在需要功能、实际 bug 修复或重要依赖修复时更新. 验收覆盖自己使用的主流程, 不以所有上游历史测试全部通过为交付标准.
- 合并成功只表示 Git 层面完成, 仍需确认没有重新引入旧登录门禁、ACP 默认配置或外部 CLI 启动路径.
- 即使彻底删除 ACP 仍可同步上游, 只是核心架构差异需要人工判断. 保留废弃源码不会自动降低合并成本, 也不应为假想的同步便利长期保留无用实现.

6. 当前结论与责任边界
- 可按个人日常主流程试用, 但不是源码级彻底移除 ACP, 也不是所有产品功能逐项验收完成.
- Crew 成员完整能力配置、完整定时任务执行及完全隔离的新系统安装仍需后续按实际需要处理, 不应靠伪造能力标记或恢复兼容层宣称完成.
- 记录中的旧上游 HTTP 500/503 是某次复验的历史结果, 不表示所有后续调用失败; 此后实际 cron 查询与审批闭环已成功.
- 后续判断以实际代码和本次执行的验证为准, 不把历史测试数字、阶段性成功或未执行的建议当作当前全面完成的证据.
